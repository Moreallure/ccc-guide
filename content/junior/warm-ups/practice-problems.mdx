# Practice Problems

You can read a hundred walkthroughs and still freeze at a blank editor. The fix
is solving problems yourself, and the best ones to start with are real J1 and
J2 problems from past contests.

This module works through three of them, from 2025 and 2024. They look
different on the surface, but all three come down to the same approach as the
last module: read carefully, work out what is actually being asked, and
translate it directly into code.

Try each problem on your own before reading its walkthrough. A wrong attempt
teaches you more than a solution you only read.

## J1 Walkthrough: Roller Coaster Ride

</ProblemSections>

### Solution

The entire problem is one comparison. The train holds \\(C \\times P\\)
people, and you ride if your place in line falls within that capacity:

\\[
N \\leq C \\times P
\\]

Sample 2 is worth a second look. You are 12th in line and the train holds
\\(4 \\times 3 = 12\\) people, so you take the last seat — being exactly at
the limit still counts as getting on.

### Implementation

<LangTabs items={['Python', 'C++']}>
  <Tab value="Python">

```python
N = int(input())
C = int(input())
P = int(input())

if N <= C * P:
    print("yes")
else:
    print("no")
```

  </Tab>
  <Tab value="C++">

```cpp
#include <bits/stdc++.h>
using namespace std;

int main() {
    int N, C, P;
    cin >> N >> C >> P;

    if (N <= C * P) {
        cout << "yes\n";
    } else {
        cout << "no\n";
    }

    return 0;
}
```

  </Tab>
</LangTabs>

## J2 Walkthrough: Donut Shop

</ProblemSections>

### Solution

Keep a running total. Start with the \\(D\\) donuts the shop opens with, then
process the \\(E\\) events one at a time: a `+` adds \\(Q\\) donuts, a `-`
removes them. When the events run out, the total is the answer.

One line in the input specification does the work for us: every sale is
guaranteed to have enough donuts in stock. The total never goes negative, so
there is nothing to check and nothing to clamp.

### Implementation

<LangTabs items={['Python', 'C++']}>
  <Tab value="Python">

```python
D = int(input())
E = int(input())

for _ in range(E):
    event = input()
    Q = int(input())

    if event == "+":
        D += Q
    else:
        D -= Q

print(D)
```

  </Tab>
  <Tab value="C++">

```cpp
#include <bits/stdc++.h>
using namespace std;

int main() {
    int D, E;
    cin >> D >> E;

    for (int i = 0; i < E; i++) {
        char event;
        int Q;
        cin >> event >> Q;

        if (event == '+') {
            D += Q;
        } else {
            D -= Q;
        }
    }

    cout << D << '\n';

    return 0;
}
```

  </Tab>
</LangTabs>

## J2 Walkthrough: Dusa and the Yobis

</ProblemSections>

### Solution

This is the first problem where the input has no count — you aren't told how
many Yobis there are. You just read sizes and react to each one: if the Yobi
is smaller than Dusa, Dusa eats it and grows; if it is the same size or
bigger, Dusa runs away and the process ends.

The problem guarantees that a Yobi big enough to stop Dusa will eventually
appear, so a loop that reads until it breaks is safe to write. That guarantee
is what lets you skip any end-of-input handling entirely.

### Implementation

<LangTabs items={['Python', 'C++']}>
  <Tab value="Python">

```python
D = int(input())

while True:
    size = int(input())

    if size >= D:
        break

    D += size

print(D)
```

  </Tab>
  <Tab value="C++">

```cpp
#include <bits/stdc++.h>
using namespace std;

int main() {
    int D;
    cin >> D;

    int size;
    while (cin >> size) {
        if (size >= D) {
            break;
        }

        D += size;
    }

    cout << D << '\n';

    return 0;
}
```

  </Tab>
</LangTabs>

## Key Takeaways

None of these problems needs anything beyond input, a condition, and a loop.
J1 and J2 reward careful reading translated directly into code, and the
specifications pay you back for it: the roller coaster samples show that
being exactly at capacity still counts, the donut spec promises that sales
never exceed stock so there is nothing to check, and Dusa guarantees the loop
terminates so there is no end-of-input handling to write.

When a problem feels harder than it should, the missing piece is usually in
the specification, not in the code.

text instead of numbers.
